# 写后语义自检

脚本校验结构，以下问题检查内容。按本次修改相关部分自检，不额外建立审批流程。

## 记录是否必要

- 能否指出这条理由帮助后来的维护者避免的具体错误？
- 是否已在代码、测试、现有文档或另一篇 Note 中充分表达？
- 是否只包含当前工程的内容，未混入外部全局规则或私人配置？

若没有独立持久价值，合并到已有归属或不新建。

## 内容是否成立

- **Problem**：脱离具体方案仍能理解问题、约束与不处理的后果。
- **Decision / Proposal**：说明选择与适用范围；状态反映真正的实现进度，不把已批准写成已完成。
- **Alternatives**：只包含真实考虑过的方案，公平描述取舍；无数量要求，允许“无”或说明未记录。
- **Consequences**：包含已知收益、代价和限制；有需要才写重访条件，未测量就不声称相对提升。
- **Verification**：区分实际执行、结果与未验证部分。Note 格式通过不代表工程测试通过。
- **维护关系**：归属唯一，相关引用有效；新决定没有悄悄覆盖旧决定的相反理由。

发现事实问题或可补足的内容，在授权范围内直接修正。只有影响结果的重要未决取舍才集中询问；不要为每篇要求一次确认或为凑备选发起新研究。

## 交付时怎么说

在整个任务的最终汇报中，合并说明记录更新、实际验证和重要剩余缺口即可。没有更新 Note 且不影响理解时，无需专门制造一项汇报；需要解释时说明具体免写理由。

缺口应落到具体内容与影响，例如“迁移路径只做静态检查，尚未运行恢复测试”。不要使用“语义通过”暗示已经证明正确，也不需要逐篇重复固定自检模板。
