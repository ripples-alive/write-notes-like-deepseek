# Notes 行文自检

让不了解当时会话的维护者看懂决定及其适用条件。保留工程理由与证据，删除对理解无用的讨论过程。

## 写清必要的信息

- 说明具体主体、选择、条件和后果。只补与决定有关的时序、所有权、失败方式和例外，不要求每段都包含全部要素。
- 不复述代码或整个 diff。能由类型、测试和现有文档表达的规则放在对应位置；Note 解释仍未表达的理由。
- 一个事实在其归属位置讲清，其余地方链接，不复制多份规则。
- `implemented` 的决定描述已落实的安排；计划、假设、未执行的测试应保持真实状态。
- 对备选公平陈述其合理性，再说明在当前约束下为何没有采用。没有真实备选或证据时如实说明。
- 后果包含已知收益和代价；没有基线不使用“更快”“成本下降”等实测语气。

## 去掉会话依赖，保留必要历史

| 原表述或内容 | 处理 |
|---|---|
| “前面第七点”“草稿 v3 已解释” | 链接已存在的具体文档，或在本篇补足必要理由 |
| “本轮先这样”“下次再看” | 说明实际适用范围、限制和已知未决事项 |
| 大段对话、尝试流水账、逐步推导 | 提炼为决定、理由、真实备选和证据 |
| “应该没问题” | 给出实际验证结果，或明确未验证的部分 |
| “先写入再通知” | 若顺序承担一致性或恢复保证，保留并说明原因 |
| 事故时间、旧方案失败条件、实测来源 | 与理由相关就保留，不因属于历史叙述而删除 |

已提交的仓库文档、测试路径、可访问的 Issue 或 PR 可作来源。仅有当时参与者能理解的序号不能作长期引用。当前状态说明应准确，但无需删掉解释决定变化所必需的历史。

## 内容边界

工程记录只保存本工程需要维护的内容。个人或组织的全局 Agent 规则、账号、外部工作区结构和跨项目同步流程在其外部归属处维护，不复制进 Notes。

公共模板只使用通用占位符，不带真实项目、用户、内部链接或配置实例。不要把公开 Skill 仓库当作宿主工程的笔记存储空间。

## 避免过度删改

删改后检查：是否把“必须”变成“可以”，把计划变成事实，丢失来源或测量条件，或移除了仍有用的失败教训。只修改当前任务相关内容，不把本次发现扩张成无关的全文改写。
