# Class 分类

只在确定存在需要保留的工程理由后分类。修改行为、跨文件或重构本身不构成新建 Note 的条件。

| Class | 记录的决定 |
|---|---|
| `feature` | 面向用户或下游的能力，以及需要解释的不显然行为选择 |
| `bug-fix` | 缺陷背后的原因、修复取舍或值得保留的失败教训 |
| `simplification` | 减少能力、兼容面、状态或维护负担的取舍 |
| `architecture` | 模块职责、依赖关系、数据流、所有权和运行时结构 |
| `process` | 当前工程的工具链、检查、发布和协作方式 |
| `testing` | 测试范围、策略、隔离方式和基础设施 |

## 边界

- `architecture` 关注工程内部如何组织和运行；`process` 关注围绕本工程的工具与工作方式。个人或组织的全局 Agent 规则不属于这里的 `process`。
- 行为不变的重构仍可能改变架构；它不自动属于 `simplification`。只有维护负担或能力范围的收缩是决定重点时，才使用 `simplification`。
- 常规功能、局部修复、机械重构无需因为存在对应 class 就新建记录。
- 一篇通常只用一个 class，按未来读者最可能查找的理由选，不按改动文件数量选。

## 与实现的对应

`scripts/agent-note-tree.ts` 中的 `AGENT_NOTE_CLASSES` 定义六个合法目录。扩展分类时，需要同时更新校验器、文档和相关模板；不为单次任务临时增加分类。
