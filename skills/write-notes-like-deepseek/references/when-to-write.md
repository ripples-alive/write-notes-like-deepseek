# 何时写、何时改与决策流转

Note 保存代码、测试和现有文档尚未表达的持久工程理由。判断依据是未来需要避免的具体错误或重新评估的取舍，而不是改动规模、文件数量或用户说了“决定”。

## 1. 先找现有归属

阅读相关模块文档和已有链接，按机制名搜索 `proposed`、`implemented`、`rejected`。日常检索排除 `archived`，需要解释历史时再读。

| 检索结果 | 处理 |
|---|---|
| 已有 Note 解释同一决定 | 更新原篇需要同步的事实或证据 |
| 相关理由已在代码、测试或现有文档中充分表达 | 更新该位置，不另建 Note |
| 只有部分重叠 | 明确各篇适用范围，必要时互链 |
| 新篇将完全吸收旧篇 | 先保留旧篇独有理由与证据，再处理重复与入站链接 |
| 无现有归属，且有独立的持久理由 | 创建最短的足够记录 |

只处理与当前任务直接相关的记录。发现其他整理机会，不自动扩大修改范围。

## 2. 原篇同步与决定反转

核心理由不变时，直接修正路径、符号、参数、限制与验证证据。无需为改名追加日期流水账，也无需把参数变动另立一篇。

决定或核心理由反转时，新建记录说明变化的条件与新取舍，并链接旧决定。旧理由需要保留，不能把原来的 `Decision` 改成相反结论。部分取代时，标明旧篇仍适用的范围；仍有现行约束的内容保持活跃。

`implemented` 的 `Decision` 描述当前已落实的安排。`Problem`、失败教训和验证记录可以保留必要的时间、历史原因与来源，不为强制现在时而丢失证据。

## 3. 状态由事实决定

- 有值得保留的方案，但选择或实现仍未完成：`proposed`。
- 当前任务已落实决定：可以直接 `implemented`，不需要补造提案或评审记录。
- 已同意方案但尚未实现：仍是 `proposed`。
- 方案被否决或停止推进：有防重犯价值则 `rejected`，否则按任务授权处理删除，不进入归档。

`proposed → implemented` 与代码、相关文档在同一 PR 或同批变更中完成：

1. 移动到 `implemented/<class>/`，保留首次提出日的文件名。
2. 更新 `Status`，将 `Proposal` 改为 `Decision`，写成已落实事实。
3. 将实际影响、剩余限制和验证结果归入 `Consequences`、`Testing` 或 `Verification`，删除失效的计划和验收标题。
4. 修复所有受影响的引用，运行三个 Note 校验器。

未做完的实现或验证不能改写成完成。范围已缩小的决定应明确已落实范围；仍有价值的剩余方案可单独保留，不用状态掩盖缺口。

## 4. 替代、合并与归档

完全替代旧方案时，先清点其中仍有价值的约束、真实备选、失败条件、代价、重访条件和验证缺口。

- 这些内容仍指导当前或可预见的工作：转入新的活跃记录，或保留旧篇适用部分。
- 新篇已经完整吸收全部有用内容，旧篇只是重复：在授权范围内删除旧篇，并修复引用。
- 旧篇已无现行约束，但有独立历史追溯价值：按 [archiving.md](archiving.md) 归档。

不能因为“已经做完”或“年代久远”归档仍有用的理由，也不能只靠 Git 历史保存读者仍需要的约束。归档历史不充当当前工程规则。

## 5. 协作与澄清

事实先从工程材料中查证。沿用当前任务的授权和已经作出的选择；只有影响结果的重要未决取舍需要集中提出，并给出已知约束与建议。

同一个决定由一名 Agent 负责最终记录。其他参与者提供事实、候选方案或验证结果，负责人合并并校验。无需每个 Agent 新建一篇，也无需每篇 Note 都经过一次新的确认仪式。
