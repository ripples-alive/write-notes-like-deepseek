# 简化机会自检

在任务已经包含清理或重构时按需使用，不自动把功能修改扩展成全库简化。

## 值得检查的信号

- 多处保存同一事实，需要额外同步。
- 抽象层、事件、配置或包没有明确的当前用途。
- 为没有明确需求的扩展预留了大量实现。
- 自定义实现与现有运行时能力重复，替换可能减少维护负担。
- 已退出支持范围的兼容逻辑仍增加复杂度。

这些是调查线索，不是删除许可。内部没有调用者不等于公开 API 没有外部用户；测试、示例或发布契约也可能承担必要用途。

## 证实与取舍

先用 `rg` 搜索真实调用、导出、配置入口、测试和文档，按宿主结构判断用途。静态工具只能提供线索；反射调用、外部消费者和兼容承诺需要额外核对。

比较删除或替换后的实现、测试、文档、依赖与迁移成本。新增依赖并不必然更简单；去掉一层封装也不必然减少实际维护负担。

小而确定的清理通常直接随任务完成，不需要 Note，也不自动新增 TODO 或任务清单。若存在未来可能被推翻的持久取舍，再记录理由、牺牲的能力、适用限制和有意义的重访条件。

## 与 Notes 的衔接

决定或实现尚未完成且值得记录时，使用 `proposed/simplification`；已落实则可直接使用 `implemented/simplification`。先搜索已有归属，避免为同一次简化建立多篇记录。

单纯行为不变的重构不自动属于此类；结构性决定可归 `architecture`，无独立理由的改动免写。仍指导未来工作的重要限制保持活跃，归档按 [archiving.md](archiving.md) 判断。
